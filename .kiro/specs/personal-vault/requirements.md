# Requirements Document

## Introduction

This document defines the requirements for evolving the current personal link manager (level 1) into a full-featured Personal Digital Vault (level 10). The vault will allow the owner to securely store, organize, and access all types of digital assets — links, images, documents, passwords, notes, and arbitrary files — from any device after deployment. The system is built on the existing React 19 + TypeScript SPA running on the Creao platform, and must provide strong security, privacy, and cross-device accessibility.

## Glossary

- **Vault**: The personal digital vault application — the system under specification.
- **Owner**: The single authenticated user who owns and operates the Vault.
- **Vault_Item**: A generic unit of stored content in the Vault (link, image, document, password, note, or file).
- **Collection**: A named group of Vault_Items created by the Owner for organization.
- **Tag**: A user-defined label that can be applied to one or more Vault_Items for cross-collection filtering.
- **Password_Entry**: A Vault_Item of type "password" containing a service name, username, password value, and optional notes.
- **Note**: A Vault_Item of type "note" containing rich or plain text content.
- **File_Entry**: A Vault_Item of type "file", "image", or "document" containing binary content stored via the Creao DataStore.
- **Link_Entry**: A Vault_Item of type "link" containing a URL and display name (backward-compatible with existing data).
- **Master_Password**: The single secret credential used to unlock the Vault session.
- **Session**: An authenticated browser session established after the Owner enters the correct Master_Password.
- **Encryption_Key**: A cryptographic key derived from the Master_Password used to encrypt sensitive Vault_Item fields client-side.
- **DataStore**: The Creao platform's ORM-backed persistent storage layer used for server-side persistence.
- **Search_Index**: An in-memory index built at session start to enable fast full-text search across all Vault_Items.
- **Clipboard**: The operating system clipboard used for copy operations.
- **Auto_Lock**: The mechanism that terminates a Session after a configurable period of inactivity.
- **Backup**: A portable, encrypted export of all Vault_Items.
- **Password_Generator**: A utility that produces random, configurable passwords.
- **Decoy_Page**: A fake error page displayed after successful Master_Password entry, designed to appear as a broken application to unauthorized observers.
- **TOTP_Code**: A time-based one-time password generated by Microsoft Authenticator, valid for a single 30-second window.
- **Section_Email_Verification**: A silent email-based verification step triggered when the Owner navigates to a vault section or initiates a file download.
- **Verification_Email**: An email sent to the Owner's registered address containing a single-use verification link.
- **Silent_Verification**: A UX pattern in which the Vault performs a verification step with no visible UI feedback — no spinner, no message, no toast — so the interface appears unresponsive to unauthorized observers.
- **Aragon2**: The Aragon 2 UI component framework used for all Vault interface components.
- **UUID_Library**: The `uuid` npm package used to generate RFC 4122-compliant unique identifiers for all Vault_Items and related records.
- **Zod**: The `zod` npm package used for runtime schema validation of all data entering or leaving the Vault.

## Requirements

### Requirement 1: Unified Multi-Type Item Storage

**User Story:** As the Owner, I want to store links, images, documents, passwords, notes, and arbitrary files in one place, so that I have a single vault for all my digital assets.

#### Acceptance Criteria

1. THE Vault SHALL support Vault_Item types: `link`, `image`, `document`, `password`, `note`, and `file`.
2. WHEN the Owner creates a Vault_Item, THE Vault SHALL persist it to the DataStore with a unique ID generated by the UUID_Library, type, title, creation timestamp, and update timestamp.
3. WHEN the Owner updates a Vault_Item, THE Vault SHALL update the item in the DataStore and record the new update timestamp.
4. WHEN the Owner deletes a Vault_Item, THE Vault SHALL remove it from the DataStore permanently.
5. THE Vault SHALL migrate all existing Link_Entry records from localStorage to the DataStore on first launch after upgrade, preserving all existing fields.
6. WHEN migration completes successfully, THE Vault SHALL clear the legacy localStorage key `akash_links_v1`.
7. WHEN any data object enters or exits the Vault's data layer, THE Vault SHALL validate it against the corresponding Zod schema and reject any object that fails validation.
8. THE Vault SHALL render all UI components using the Aragon2 component framework.

---

### Requirement 2: File and Media Upload

**User Story:** As the Owner, I want to upload images, documents, and arbitrary files into the Vault, so that I can access them from any device.

#### Acceptance Criteria

1. WHEN the Owner selects a file for upload, THE Vault SHALL accept files up to 100 MB in size.
2. IF the Owner selects a file exceeding 100 MB, THEN THE Vault SHALL display an error message stating the file size limit and reject the upload.
3. WHEN a file upload completes, THE Vault SHALL store the file via the Creao DataStore upload API and record the returned file URL in the File_Entry.
4. WHEN the Owner views a File_Entry of type `image`, THE Vault SHALL render an inline image preview.
5. WHEN the Owner views a File_Entry of type `document` or `file`, THE Vault SHALL provide a download link and display the file name and size.
6. WHILE a file upload is in progress, THE Vault SHALL display a progress indicator showing the percentage of bytes uploaded.

---

### Requirement 3: Password Manager

**User Story:** As the Owner, I want to store and manage passwords for my accounts, so that I never lose access to my services.

#### Acceptance Criteria

1. WHEN the Owner creates a Password_Entry, THE Vault SHALL store the service name, username, password value, URL (optional), and notes (optional).
2. THE Vault SHALL encrypt the password value field of every Password_Entry using the Encryption_Key before persisting it to the DataStore.
3. WHEN the Owner views a Password_Entry, THE Vault SHALL display the password value as masked characters by default.
4. WHEN the Owner clicks "Reveal" on a Password_Entry, THE Vault SHALL decrypt and display the password value in plain text for 30 seconds, then re-mask it automatically.
5. WHEN the Owner clicks "Copy Password" on a Password_Entry, THE Vault SHALL copy the decrypted password value to the Clipboard without displaying it on screen.
6. THE Password_Generator SHALL produce passwords of configurable length (8–64 characters) with configurable character sets (uppercase, lowercase, digits, symbols).
7. WHEN the Owner requests a generated password, THE Password_Generator SHALL produce a cryptographically random password matching the configured parameters.

---

### Requirement 4: Notes with Rich Text

**User Story:** As the Owner, I want to write and store notes with formatting, so that I can keep structured information in the Vault.

#### Acceptance Criteria

1. WHEN the Owner creates a Note, THE Vault SHALL provide a text editor supporting bold, italic, underline, headings, bullet lists, numbered lists, and inline code formatting.
2. THE Vault SHALL store Note content as a serialized rich-text format (e.g., Markdown or a portable JSON document format).
3. WHEN the Owner views a Note, THE Vault SHALL render the stored rich-text content as formatted HTML.
4. THE Pretty_Printer SHALL serialize Note content back into the stored format without data loss.
5. FOR ALL valid Note objects, parsing then printing then parsing SHALL produce an equivalent Note object (round-trip property).

---

### Requirement 5: Collections and Tags

**User Story:** As the Owner, I want to organize Vault_Items into collections and tag them, so that I can find what I need quickly.

#### Acceptance Criteria

1. THE Vault SHALL allow the Owner to create, rename, and delete Collections.
2. WHEN the Owner deletes a Collection, THE Vault SHALL move all Vault_Items in that Collection to an "Uncategorized" default Collection rather than deleting the items.
3. THE Vault SHALL allow the Owner to assign one or more Tags to any Vault_Item.
4. WHEN the Owner filters by a Tag, THE Vault SHALL display all Vault_Items that have that Tag, regardless of Collection.
5. WHEN the Owner moves a Vault_Item to a different Collection, THE Vault SHALL update the item's collection reference in the DataStore.

---

### Requirement 6: Full-Text Search

**User Story:** As the Owner, I want to search across all my stored items by keyword, so that I can find anything instantly.

#### Acceptance Criteria

1. WHEN the Owner types in the search field, THE Vault SHALL display matching Vault_Items within 300 ms of the last keystroke.
2. THE Search_Index SHALL match against Vault_Item title, tags, collection name, and text content fields (URL for links, notes body, service name for passwords, file name for files).
3. WHEN the search query is empty, THE Vault SHALL display all Vault_Items in the current view.
4. THE Vault SHALL highlight the matching search term within displayed Vault_Item titles and text snippets.

---

### Requirement 7: Authentication and Session Security

**User Story:** As the Owner, I want the Vault to be protected by a strong password and to lock automatically, so that no one else can access my data.

#### Acceptance Criteria

1. WHEN the Owner submits the Master_Password on the lock screen, THE Vault SHALL derive the Encryption_Key using PBKDF2 with SHA-256, a minimum of 100,000 iterations, and a stored salt.
2. IF the Owner submits an incorrect Master_Password, THEN THE Vault SHALL increment a failed-attempt counter and display the remaining attempts.
3. WHEN the failed-attempt counter reaches 5, THE Vault SHALL lock the application for 15 minutes before accepting further attempts.
4. WHILE a Session is active and no user interaction has occurred for the configured Auto_Lock duration (default 15 minutes), THE Vault SHALL terminate the Session and display the lock screen.
5. WHEN the Owner locks the Vault manually, THE Vault SHALL clear the Encryption_Key from memory and display the lock screen immediately.
6. THE Vault SHALL store the Master_Password salt in the DataStore and never transmit or store the Master_Password itself.
7. WHEN the Owner changes the Master_Password, THE Vault SHALL re-encrypt all encrypted fields with a new Encryption_Key derived from the new password.

---

### Requirement 8: Client-Side Encryption

**User Story:** As the Owner, I want sensitive data to be encrypted before it leaves my browser, so that even the server cannot read my passwords or private notes.

#### Acceptance Criteria

1. THE Vault SHALL encrypt the password value field of all Password_Entry items using AES-256-GCM with the Encryption_Key before sending data to the DataStore.
2. WHERE the Owner marks a Note as "private", THE Vault SHALL encrypt the Note content field using AES-256-GCM with the Encryption_Key before persisting.
3. THE Vault SHALL perform all encryption and decryption operations using the Web Crypto API in the browser.
4. WHEN the Vault reads an encrypted field from the DataStore, THE Vault SHALL decrypt it using the Encryption_Key held in the current Session before displaying it.
5. IF decryption of a field fails, THEN THE Vault SHALL display an error indicator on that Vault_Item and log the error without exposing raw ciphertext to the Owner.

---

### Requirement 9: Cross-Device Accessibility

**User Story:** As the Owner, I want to access my Vault from any device after deployment, so that my data is always available wherever I am.

#### Acceptance Criteria

1. THE Vault SHALL persist all Vault_Items to the Creao DataStore so that data is available from any device with a browser.
2. THE Vault SHALL render correctly on viewport widths from 320 px (mobile) to 2560 px (desktop) using responsive layout.
3. WHEN the Owner accesses the Vault on a mobile device, THE Vault SHALL display a touch-optimized interface with tap targets of at least 44 × 44 px.
4. THE Vault SHALL function as a Progressive Web App (PWA), allowing the Owner to install it on a device home screen.
5. WHEN the Vault is installed as a PWA and the device is offline, THE Vault SHALL display a clear offline indicator and allow read-only access to previously loaded Vault_Items cached by the service worker.

---

### Requirement 10: Backup and Export

**User Story:** As the Owner, I want to export and import all my vault data, so that I have a portable backup independent of the platform.

#### Acceptance Criteria

1. WHEN the Owner requests an export, THE Vault SHALL produce a single encrypted JSON file containing all Vault_Items and their metadata.
2. THE Vault SHALL encrypt the export file using AES-256-GCM with a key derived from the Master_Password.
3. WHEN the Owner imports a Backup file and provides the correct password, THE Vault SHALL decrypt and restore all Vault_Items to the DataStore.
4. IF the Owner provides an incorrect password during import, THEN THE Vault SHALL display an error and not modify any existing Vault_Items.
5. FOR ALL valid Vault exports, exporting then importing with the correct password SHALL produce a Vault state equivalent to the original (round-trip property).

---

### Requirement 11: Audit Log

**User Story:** As the Owner, I want to see a log of recent activity in my Vault, so that I can detect any unauthorized access.

#### Acceptance Criteria

1. THE Vault SHALL record an audit log entry for each of the following events: Session start, Session end, Vault_Item created, Vault_Item updated, Vault_Item deleted, failed login attempt, and Backup exported.
2. WHEN the Owner views the audit log, THE Vault SHALL display entries in reverse chronological order showing event type, timestamp, and Vault_Item title (where applicable).
3. THE Vault SHALL retain audit log entries for a minimum of 90 days.
4. THE Vault SHALL store audit log entries in the DataStore and encrypt the Vault_Item title field within each entry using the Encryption_Key.

---

### Requirement 12: Settings and Customization

**User Story:** As the Owner, I want to configure the Vault's behavior and appearance, so that it fits my personal workflow.

#### Acceptance Criteria

1. THE Vault SHALL allow the Owner to configure the Auto_Lock timeout duration with options of 5, 15, 30, or 60 minutes, or "Never".
2. THE Vault SHALL allow the Owner to toggle between light and dark color themes.
3. THE Vault SHALL persist all settings to the DataStore so that they are consistent across devices.
4. WHEN the Owner changes the Master_Password in Settings, THE Vault SHALL require the Owner to enter the current Master_Password before accepting the new one.
5. THE Vault SHALL allow the Owner to configure the default view (grid or list) for Vault_Items.

---

### Requirement 13: Three-Layer Authentication Flow

**User Story:** As the Owner, I want the Vault to require three sequential authentication factors before granting access, so that an unauthorized observer cannot gain entry even if they witness the first factor being entered.

#### Acceptance Criteria

1. THE Vault SHALL enforce authentication in exactly three sequential layers: Master_Password verification (Layer 1), TOTP_Code verification via the Decoy_Page (Layer 2), and per-section Section_Email_Verification (Layer 3).
2. WHEN the Owner submits the correct Master_Password on the lock screen, THE Vault SHALL transition to the Decoy_Page rather than to the main vault view.
3. WHEN the Owner submits an incorrect Master_Password, THE Vault SHALL remain on the lock screen and apply the existing failed-attempt counter and lockout rules defined in Requirement 7.
4. WHEN the Owner successfully completes Layer 2 TOTP_Code verification on the Decoy_Page, THE Vault SHALL transition to the main vault view showing the section navigation buttons.
5. WHEN the Owner clicks a section navigation button in the main vault view, THE Vault SHALL silently trigger a Section_Email_Verification before displaying the section contents, with no visible UI feedback during the verification wait.
6. WHEN the Owner clicks a download control on any File_Entry within a section, THE Vault SHALL silently trigger a Section_Email_Verification before initiating the download, with no visible UI feedback during the verification wait.
7. IF any authentication layer fails, THEN THE Vault SHALL remain on the current layer's screen without displaying any error message, hint, or indication that a verification step exists.

---

### Requirement 14: Decoy Error Page (Layer 2)

**User Story:** As the Owner, I want the page shown after entering my master password to look like a broken application, so that an unauthorized observer believes the app is non-functional and does not attempt further access.

#### Acceptance Criteria

1. WHEN the Owner is directed to the Decoy_Page, THE Vault SHALL render a page that visually resembles a genuine application error, displaying a message such as "The application is broken and currently unavailable" with styling consistent with a real system error screen.
2. THE Decoy_Page SHALL contain a single interactive element styled to appear as an error code or error details button, labeled "Error", with no visual indication that it is a secret entry point.
3. THE Decoy_Page SHALL contain no text, label, placeholder, tooltip, or aria-label that references OTP entry, verification, authentication, or any secret action.
4. WHEN the Owner clicks the "Error" button on the Decoy_Page, THE Vault SHALL reveal a plain text input field with no label, placeholder, or surrounding text that indicates its purpose.
5. WHEN the Owner submits a value in the hidden input field, THE Vault SHALL validate it as a TOTP_Code against the Owner's registered Microsoft Authenticator secret using the `otpauth` library.
6. WHEN the submitted TOTP_Code is valid, THE Vault SHALL transition to the main vault view.
7. WHEN the submitted TOTP_Code is invalid or expired, THE Vault SHALL dismiss the input field and return the Decoy_Page to its default broken-app appearance, with no error message or indication of what occurred.
8. WHILE the Decoy_Page is displayed, THE Vault SHALL not render any element that reveals the existence of a second authentication layer to an observer who does not know the secret interaction.

---

### Requirement 15: Silent Email Verification for Vault Sections (Layer 3)

**User Story:** As the Owner, I want opening any vault section to silently send me a verification email, so that an unauthorized user who reaches the vault view cannot access any section contents without my email confirmation.

#### Acceptance Criteria

1. WHEN the Owner clicks a section navigation button (Links, Docs, Files, Images, Passwords, or Notes), THE Vault SHALL immediately dispatch a Verification_Email to the Owner's registered email address without displaying any loading indicator, spinner, toast, or status message.
2. WHILE the Vault is awaiting email verification for a section, THE Vault SHALL render the section button in its default state with no visual change, making the interface appear unresponsive to an observer.
3. WHEN the Owner clicks the "Verify" link in the Verification_Email, THE Vault SHALL open or refresh the section view and display the section's contents.
4. IF the Verification_Email link expires before the Owner clicks it, THEN THE Vault SHALL silently discard the pending verification and require the Owner to click the section button again to trigger a new Verification_Email.
5. THE Vault SHALL generate a unique, single-use token for each Verification_Email using the UUID_Library, and invalidate the token immediately after it is used.
6. THE Vault SHALL validate the structure and expiry of each verification token using Zod before granting section access.

---

### Requirement 16: Silent Email Verification for File Downloads

**User Story:** As the Owner, I want downloading any file, document, or image to require a separate email verification, so that an unauthorized user who reaches a section view cannot exfiltrate any stored files.

#### Acceptance Criteria

1. WHEN the Owner activates a download control on any File_Entry (file, document, or image), THE Vault SHALL immediately dispatch a Verification_Email to the Owner's registered email address without displaying any loading indicator, spinner, toast, or status message.
2. WHILE the Vault is awaiting email verification for a download, THE Vault SHALL render the download control in its default state with no visual change, making the interface appear unresponsive to an observer.
3. WHEN the Owner clicks the "Verify" link in the Verification_Email, THE Vault SHALL initiate the file download in the browser.
4. IF the Verification_Email link expires before the Owner clicks it, THEN THE Vault SHALL silently discard the pending download verification and require the Owner to activate the download control again to trigger a new Verification_Email.
5. THE Vault SHALL generate a unique, single-use download token for each Verification_Email using the UUID_Library, and invalidate the token immediately after the download begins.
6. THE Vault SHALL validate the structure and expiry of each download token using Zod before initiating the file download.
